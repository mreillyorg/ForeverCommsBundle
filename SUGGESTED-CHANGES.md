## H. Architecture decisions recorded so they are not re-litigated

| # | Decision | Why it came up | Outcome |
| --- | --- | --- | --- |
| 45 | Should the consumers embed `ForeverCommsVoice` as a LibStub-style library under `Libs/` instead of depending on it as a separate addon? | The hard `## Dependencies` means a consumer installed on its own is refused by the client. Embedding is the conventional WoW answer to that | **REJECTED — keep the separate addon.** The blocking reason is technical, not stylistic: `ForeverCommsVoice` declares `## SavedVariablesPerCharacter: ForeverCommsVoiceCharDB` and persists both the voice profile and the queue settings there. An embedded library is loaded through the consumer's TOC, has no TOC of its own, and therefore **cannot declare SavedVariables** — only addons can. Embedding would force that shared state into a consumer's database, which (a) breaks the project's own "never let one package write another's table" invariant, (b) makes `A.char.voice` and `ForeverCommsVoiceCharDB.voice` being the *same table object* impossible or very fragile, and (c) creates an install-order ownership problem needing a second, bidirectional migration alongside the existing latched `V:MigrateLegacy`. Separately, the library owns `/fcv`, a Settings AddOn category and a named window — surfaces that belong to an addon, since with two embedded copies "which one registers the slash command" becomes a load-order accident. It would also trade a rule enforced by the release process ("a breaking `V:Render` contract change means releasing all three together") for LibStub's within-name backward-compatibility discipline, enforced only by care. Finally the distribution problem it would solve is already solved: the root `.pkgmeta` bundles all three folders in every archive and the combined installer prepends the library to any consumer-only selection, so a library-less install is unreachable. Note this also reverses nothing — `release-packaging.md` already records "Nothing is vendored. No `externals` block, no `Libs/`, no `embeds.xml`" as deliberate |
| 46 | Make both consumers refuse to load when the library is absent, from `Core.lua` | GroupComms guarded every library call and degraded silently to English-only wording with no shared queue. GuildComms did error, but from `VoiceBridge.lua` — the second TOC file — so `Core.lua` had already published the namespace and created the event dispatcher | **DONE — both addons.** Each `Core.lua` now refuses to load without `_G.ForeverCommsVoice`, as the **first statement** after the vararg capture, so the namespace global is never published, the dispatcher is never created and the `Bindings.xml` handlers see nil. The addon goes inert with one clear message instead of half-running.
